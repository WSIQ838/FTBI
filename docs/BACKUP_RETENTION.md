# Managed encrypted backup inventory and retention

scripts/backup_catalog.py manages a deliberately initialized private backup directory. Initialization accepts an empty directory and binds a marker to its resolved path. Existing unmanaged backups are not automatically enrolled or deleted. Copying/moving a store requires an explicit reviewed migration; do not edit markers casually. Restrict filesystem access to the backup operator. Symlinks and multiply linked/nonregular archive files are rejected. A catalog lock prevents overlapping managed work; after a crash, a trusted operator must establish that no process is running before handling a stale lock.

The run action invokes the repository's fixed encrypted-backup script with the selected store as BACKUP_DIR. The script needs the existing PostgreSQL client, age utility and public encryption recipient. It verifies the dump's table of contents, encrypts it, then gives the archive a unique filename so two backups in one second cannot overwrite each other. Plaintext temporary dumps are removed on normal/error exit; host crashes and snapshots remain infrastructure risks requiring encrypted temporary storage. Private decryption keys are never required for backup creation.

A successful run atomically records an archive manifest containing filename, size, creation time and SHA-256, plus a private status file with last attempt and last success. Failed runs record generic failed status and exit nonzero without printing provider stderr or credentials. A partial/unmanaged archive is retained for investigation rather than silently pruned. Monitoring reads the status file and can emit a backup failure/staleness notice on its next scheduled check. If the application/database is down, an external scheduler/monitor must handle the nonzero exit; none is deployed by this change.

Retention is dry-run by default. The prune action validates every managed manifest and file digest before planning deletion. A corrupt manifest or archive stops the operation. At least seven days and two archives must be retained; defaults are 30 days and seven archives. The newest keep-count archives are always protected. Older archives qualify only when outside the age window and older than a successfully restored archive among the protected set. Explicit apply is required to delete eligible archive/manifest pairs. Unmanaged files are untouched. These conservative limits are not institutional recovery or legal-retention requirements; approved values are still needed.

mark-restored records the operator's assertion that the exact managed archive passed a disposable restore and integrity comparison. It is not itself a restore and does not prove recoverability. The encrypted recovery CI uses real PostgreSQL and age, compares all application rows after restoration, checks migrations, then marks that archive restored and evaluates a dry-run retention plan. Do not mark real archives verified without equivalent evidence.

No offsite upload, backup scheduler, key escrow, key recovery acceptance, production-scale timing, RPO/RTO or business continuity acceptance has been supplied. Local hashes do not prevent a privileged attacker rewriting both archives and manifests. Offsite immutable storage, independent audit evidence and institutional key custody remain required release work. Current scripts do not implement selective erasure from historical encrypted dumps.

Unit tests use explicitly synthetic archive bytes to test catalog boundaries, retention, corruption, locking, symlinks and failure status. Only the hosted encrypted recovery workflow establishes encryption/restore integration for a synthetic database. No production database backup or deletion was performed during development.
