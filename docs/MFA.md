# Authenticator MFA
Uses django-otp TOTP devices and session verification with device throttling and replay protection. Users can enroll via Account security, then subsequent sessions require a code. FTBI_REQUIRE_MFA=1 requires enrollment for everyone; FTBI_REQUIRE_STAFF_MFA=1 requires it for staff. Both default off in development; staff enforcement defaults on outside DEBUG. Gate covers authenticated views including Django admin. Lost-device recovery requires a verified institutional identity-recovery procedure and an authorized operator removing the device and revoking existing sessions; no self-service recovery codes yet. Protect the database and backups because TOTP secrets are stored there. MFA enrollment and verification require HTTPS outside development. This implementation requires testing, including password reset, admin login, concurrent attempts and recovery before production.


## Passkeys

An optional WebAuthn second factor is available after the normal sign-in. Device user verification (PIN or biometric verification) and presence are required; this is not passwordless login. The Passkeys page supports a private account list, enrollment and revocation. Enrollment requires password confirmation and any existing verified MFA; accounts with an enrolled passkey cannot bypass the MFA gate. Existing TOTP and single-use recovery codes remain available, including recovery for passkey-only accounts. Accounts without a usable local password cannot enroll or revoke through this password-confirmed workflow.

The feature is disabled by default. Its configuration uses `FTBI_PASSKEYS_ENABLED`, `FTBI_PASSKEY_RP_ID` and `FTBI_PASSKEY_ORIGIN`; an enabled deployment needs an approved HTTPS origin and its exact matching DNS hostname. Configuration is checked by deployment checks and every ceremony. Only explicitly enabled debug validation permits HTTP localhost. The server never derives the trusted origin from request headers. Institution domain selection, physical-device interoperability and independent MFA review remain release gates.

Challenges are random, expire after five minutes, belong to the authenticated account/session and are consumed under a row lock. Beginning another ceremony replaces that account's previous challenge. Verification enforces origin/RP, credential ownership, user handle, presence, user verification, cryptographic signature, counter progression when supported and stable backup eligibility. Cross-origin iframe ceremonies are rejected. Request sizes and attempts are bounded; each account supports eight active passkeys and 64 lifetime records before controlled maintenance is required. No private keys or biometric data are stored by FTBI. Synced passkeys and zero-counter authenticators do not provide hardware attestation or a guarantee against cloned credentials.

Revocation requires verified MFA and password confirmation, preserves a disabled credential record, emits an audit/security notification and invalidates verification based on that device on subsequent requests. Already running requests and copies in a third-party password manager are outside this revocation boundary. Generic administration is read-only for passkey records. Disabling the feature stops ceremonies but does not silently bypass an existing MFA requirement; enrolled users need an available fallback or support. There is no newly introduced helpdesk factor-reset bypass.

Server verification uses [py_webauthn registration](https://duo-labs.github.io/py_webauthn/registration.html) and [authentication](https://duo-labs.github.io/py_webauthn/authentication.html). Tests use real signed synthetic responses; the browser scenario uses Chromium's virtual authenticator. Those checks are not physical-device, institutional domain, passwordless-login or independent security acceptance.
